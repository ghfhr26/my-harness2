# 허들링 앱 작업 방식 (손으로 한 마지막 경험)

`story-service.md`가 "무엇을 위한 일인지"의 기준이라면, 이 문서는 "내가 실제로 어떻게 했는지"를 기록한다. 둘은 섞지 않는다.

## 작업 문장

1. 나는 uibowl에서 경쟁사 레퍼런스를 수집한다.
2. 레퍼런스를 토대로 분석하고 우리 서비스에 반영할 부분을 가져온다.
3. 분석 내용을 토대로 우리 서비스 화면 설계 문서를 구체화한다.
4. figma에 레퍼런스와 화면설계서를 반영한 UI 키스크린 2~3개를 390×844 사이즈로 그린다.
5. 내부 관계자들과 협의 후 컨셉 시안을 확정한다.
6. 컨펌된 시안을 기반으로 디자인 토큰과 컴포넌트를 제작하고, 화면 디자인에 들어간다.
7. 완성된 시안에서 토큰이나 컴포넌트가 우리 가이드(`design.md`)에 위반된 부분이 없는지 검토한다.

## 1. 명사 (산출물)

| 문장 | 산출물 |
|---|---|
| 1 | 경쟁사 레퍼런스 (수집본) |
| 2 | 분석 내용 / 우리 서비스에 반영할 항목 |
| 3 | 화면 설계 문서 (화면설계서) |
| 4 | UI 키스크린 2~3개 (390×844) |
| 5 | 확정된 컨셉 시안 |
| 6 | (1) 디자인 토큰·컴포넌트 |
| 6 | (2) 화면 디자인 (완성 시안) |
| 7 | 검토 결과 |

## 2. 게이트 (멈칫한 지점)

| 위치 | 멈칫한 이유 | 검사 기준 | 검사 주체 |
|---|---|---|---|
| 문장 2 후 (2→3 사이) | 반영할 기준이 없어서 매번 고민함 | 미정 (하네스 인터뷰 R5에서 결정) | 미정 |
| 문장 3 후 (3→6 사이) | 분석 → 화면 설계 → 디자인 제작 사이에는 반드시 게이트가 필요함 | 미정 (하네스 인터뷰 R5에서 결정) | 미정 |
| 문장 4 | 어떤 화면을 몇 개 그릴지 정하기 어려움 | 그릴 키스크린이 `story-service.md` 유저스토리에서 골랐는가 | 자동 검사 |
| 문장 5 | 컨펌을 받아야 다음으로 넘어갈 수 있음 | 내부 관계자 컨펌 (승인 전에는 6번 진행 불가) | 사람 (내부 관계자, 유일한 사람 컨펌) |
| 문장 7 | 하나하나 눈으로 대조해야 해서 오래 걸리고, 서체·색이 가이드와 다르게 들어간 걸 놓쳐서 다시 고친 적 있음 | `design.md` 위반 여부 (토큰·컴포넌트) | 자동 대조 후보 |

## 3. 에이전트 경계 (넘어가는 지점)

| 위치 | 넘어가는 곳 | 종류 |
|---|---|---|
| 문장 1 | 나 → uibowl | 도구 |
| 문장 4 | 나 → figma | 도구 |
| 문장 5 | 나 → 내부 관계자 | 사람 (유일) |
| 문장 3, 6 | 경계 없음 (혼자 작업) | |

## 미결 사항

- 2→3, 3→6 게이트의 검사 기준과 주체: 하네스 인터뷰 R5에서 결정
